## 2. Human-Readable Summary

`memo write` now understands banks (shared vs. private memory spaces), kinds (`self`/`episodic`/`semantic`), sessions, and the ability to mark one memory as replacing another (`--supersedes`). The delivered code follows the eleven-step build order the spec laid out almost exactly, step for step, including the three previously-open questions that were resolved before implementation started: a missing supersede target now fails with "entry not found" (not a generic validation error), pointing a write at itself is rejected the same way as any other bad supersede target, and the "you're approaching your self-entry limit" warning always counts what existed _before_ this write, not after. When updating the old entry fails after the new one has already been saved, the command clearly reports both entry ids and does not undo the new entry — exactly as specified. Every one of the story's eleven acceptance criteria has passing, targeted tests, and the full project test suite (777 tests), linting, type-checking, formatting, and dependency audit all pass cleanly on this branch. The only imperfection found is a small, harmless extra safety check in the duplicate-detection code that never actually changes behavior in practice — not a functional problem, just slightly more code than necessary.

**Order-of-operations check (§18.6's eleven steps):** Verified by direct code read of `src/commands/write.ts` — the delivered order is: (1) resolve bank/kind/policy → (2) scope check → (3) source/entry_type defaults → (4) build v2 payload incl. episodic `nextSeq`/`expires_at`/retention fields → (5) `EntryPayloadV2Schema.safeParse` → (6) `--supersedes` target checks (`getById` → bank/kind match → already-superseded) → (7) `self` soft-cap `count()` (pre-write, before dedupe/upsert) → (8) dedupe v2 + `kb`-semantic v1 fallback + unchanged duplicate-resolution flow → (9) embed + `upsert` → (10) supersede `setPayload` with the two-id failure message → (11) v2 JSON result. This matches spec §18.6 exactly, step for step. Two checks (the K3 provenance guard and the `--supersedes` self-reference guard) are evaluated _earlier_ than their nominal step number, before any I/O opens — this is consistent with, not contrary to, spec §8.3 step 1's general design principle ("Validate PRD K1–K3... before any I/O") and does not reorder any I/O-bearing step relative to another I/O-bearing step. Not classified as drift.

## 4. Drift Catalog

### D-1 — Extra, functionally-inert condition on the `kb`-semantic v1-dedupe-key fallback

- **Description:** Spec §18.5/§18.6 step 8 states the v1 dedupe key is checked "when `bank === 'kb' && kind === 'semantic'`." The delivered code (`write.ts:400`) adds a third condition, `repo !== undefined`, that is not in the spec. Because a `kb` write always requires `repo`/`org`/`domain` (enforced by the `REPO_CONTEXT_UNRESOLVED` check at step 2), this extra condition is always true whenever the other two hold — it is unreachable-in-practice and produces no observable difference in behavior for any real `kb` semantic write.
- **Impact:** Minor
- **Intent:** Undetermined (plausibly defensive coding against a hypothetical future relaxation of the `kb` repo requirement, or simply an unnecessary guard carried over from the recovered partial work mentioned in the PR body)
- **Evidence source(s):** `src/commands/write.ts` line 400; spec §18.5, §18.6 step 8; confirmed unreachable by cross-referencing the `REPO_CONTEXT_UNRESOLVED` guard at `write.ts:210-215`
- **Non-blocking note:** This drift does not affect any acceptance criterion's pass/fail status and does not block merge or completion.

No other drift items were found. All eleven acceptance criteria, the three §18.14 resolutions (AC-7 exit codes/messages, self-reference guard code, soft-cap pre-write semantics), and the non-transactional `--supersedes` failure contract match the specification exactly.
