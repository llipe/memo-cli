## Pre-Implementation Findings

Design-time analysis surfaced items that affect how the ACs must be tested. All are reported, not fixed — remediation belongs to `developer`; scope ambiguity is escalated to `product-engineer`.

### F-1 — AC5's five rejection cases are stated as a flat list but the spec's rule table has six rows (Minor, clarify before test authoring)

AC5 enumerates five rejection scenarios (`self` in `kb`; `episodic` without `session_id`; `semantic`/`agent`/empty `provenance`; `self` with retention fields; `seq` on non-episodic), but spec §18.3's rule table has six rows — it separately lists "K2 scope required in `kb`" (`repo`/`org`/`domain` missing in `kb`, error path `repo`) as its own row, which AC5 does not mention. The story's own Business Rules section says "K2 ... is enforced in the same `superRefine`," confirming K2 is in scope even though AC5's list omits it. **EC-5** in this plan tests the K2 rejection independently so it is not silently dropped from coverage; this is flagged rather than assumed, since AC5's omission could also be an intentional narrowing (K2 might be a command-side pre-check duplicated at schema level only defensively). Recommend `developer` confirm K2's schema-level test is written regardless of the AC5 wording gap.

### F-2 — "Every §8.4 default" (AC1) requires cross-referencing a table not reproduced in the story (Major, test-authoring risk)

AC1 says "every `banks.*` value" resolves "to the spec §8.4 table," but the story text does not inline that table. The five-row policy defaults table (private/self, private/episodic, private/semantic, kb/episodic, kb/semantic — each with `initial_stability_days`, `expires_in_days`, `archive_threshold`, `archive_noisy`, `promoted_grace_days`, `superseded_grace_days`, `purge_after_days`) lives only in spec §8.4. **SC-1** and **CT-1** enumerate all five rows explicitly in this plan (see Contract Validation Scenarios) so `developer`'s `config.test.ts` has a concrete, unambiguous target instead of re-deriving values from prose. A transcription error in either the implementation or a hand-written test would otherwise be easy to miss since both `KindPolicySchema` fields default via Zod `.optional()` (no default) except `purge_after_days`/`soft_cap`, which have explicit default semantics per bank type.

### F-3 — AC2 and the §18.2 note ("no default... rejects being set to a number by default") describes a Zod modeling constraint, not an independently observable behavior (Minor)

AC2's phrasing that `kb` purge "resolve[s] to `undefined` when absent" is straightforward to test via `safeParse`. However §18.2's parenthetical — "the refinement rejects `banks.kb.*.purge_after_days: undefined` being _set to a number by default_" — describes an implementation technique (no `.default()` on that field) rather than an externally observable rule distinct from AC2 itself. This plan treats AC2 as fully covered by asserting the _absent → `undefined`_ and _explicit → kept_ behaviors (SC-2); it does not add a separate test asserting "no default exists" as that is not independently observable from outside the schema (any test that could detect a rogue default would already be exercised by the absent-value case).

### F-4 — `soft_cap` and `max_tokens` boundary conditions in AC3/AC4 need explicit non-integer and negative cases beyond the story's literal examples (Minor)

AC3 and AC4 name `0` as the only explicit failing example for `soft_cap` and `max_tokens` respectively, plus "a non-integer" for `soft_cap`. Both fields are declared `z.number().int().positive()`, so the full boundary set (negative, `0`, fractional, non-numeric, `null`) is a superset of what the AC prose spells out. **EC-3** and **EC-4** cover the full boundary set so the edge-case matrix is not limited to only the two literal examples named in the AC text.

### F-5 — `normalizeEntry`'s behavior on a payload missing `timestamp_utc` is stated as "handled" without a specified output (Minor, needs confirmation)

The story's Testing Requirements name a test case ("missing `timestamp_utc` handled") but neither the story, spec §18.3, nor the technical notes state what `valid_from` becomes when both `timestamp_utc` and `valid_from` are absent from the input (the rule is `valid_from ??= timestamp_utc` when `kind !== 'episodic'` — if `timestamp_utc` is itself absent, the right-hand side is `undefined`, so `valid_from` would remain `undefined` unless `normalizeEntry` has an additional fallback such as `now()`). **EC-16** records observed behavior without hard-failing the story either way; recommend `developer` confirm the intended fallback (`undefined` vs. current-time) with `product-engineer` if it is not already decided, since a silent `now()` fallback would be a meaningful behavioral choice worth documenting in `docs/data-model.md`.

## Randomized Test Tactics

This story's compliance surface is pure functions over structured input (no I/O, no timing dependency beyond `normalizeEntry`'s `now()`-adjacent field), which makes it well suited to light property-based fuzzing over the `EntryPayloadV2Schema` rule table.

| ID   | Tactic                                                                                                                                                                                                                                                                                                                                                                                | AC                  | Seed / replay policy                                                                                                                                                                                                                                     |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RT-1 | Generate randomized combinations of `{kind, bank, session_id present/absent, source, provenance length, stability present/absent, seq present/absent}` across the 6-rule truth table; assert each combination's accept/reject outcome matches the spec §18.3 rule table exactly (a simple decision-table oracle function mirroring the six rules, independent of the implementation). | AC5, AC6            | Fixed seed (e.g., `42`) recorded in the test file; on failure, print the exact input object and expected vs. actual outcome for deterministic replay. Minimum 200 generated combinations to reach full pairwise coverage of the boolean/enum dimensions. |
| RT-2 | Fuzz `KebabOrUuid`-typed fields (`bank`, `contexts` elements) with a mix of valid kebab strings, valid UUIDs, and near-miss strings (uppercase, leading digit, double-hyphen, trailing hyphen, empty string)                                                                                                                                                                          | AC1, AC5 (contexts) | Fixed seed; each near-miss case that unexpectedly parses is reported as evidence, not auto-failed, since it may reveal a regex gap worth flagging to `developer` rather than a story-blocking defect.                                                    |
| RT-3 | Fuzz numeric boundary fields (`soft_cap`, `max_tokens`, `expires_in_days`, `promoted_grace_days`) with `{-Infinity, -1, 0, 0.5, 1, MAX_SAFE_INTEGER, NaN, null, "5" (string)}`                                                                                                                                                                                                        | AC3, AC4            | Fixed seed; deterministic table, not true randomness — listed under "random tactics" per the skill's boundary-fuzzing convention but functionally a boundary sweep.                                                                                      |

Failure triage for RT-1/RT-2/RT-3 follows the standard sequence: capture seed + input → isolate via re-run with the same seed → minimize to the smallest failing combination → classify (spec gap → `product-engineer`; implementation defect → `developer`; flaky/non-reproducing → `inconclusive` after ≤ 3 retries).
