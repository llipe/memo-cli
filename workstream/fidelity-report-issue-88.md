### Plain-language summary

This PR adds a one-time, opt-in command (`memo migrate --to-v2`) that upgrades old memory entries to the new format. I read the actual code (not just the tests), and the safety story holds up: the "preview" mode (`--dry-run`) is structurally incapable of writing anything — there's exactly one line in the whole command that writes, and it's wrapped in `if (!dryRun ...)`. There is no delete/archive call anywhere in this code path, at all, in any mode. Running it twice is safe by construction, not just by luck: the second run's own database query excludes anything already migrated, and the planner double-checks that on top. The classification rule that decides "is this a short-lived note or a permanent decision" is implemented exactly as specified, including defaulting to the safer "permanent decision" bucket when unsure (misclassifying a real decision as short-lived risks it silently expiring, which the spec explicitly calls out as the worse mistake). The one live run's numbers are internally consistent and cross-checked against the actual fixture data. The command still requires you to deliberately point it at a sandbox collection — there's no way it defaults itself onto the production data.

One nuance worth surfacing plainly: the task list's step 9.15 called for "request user confirmation before any real apply." What actually happened was the developer's pre-approved autonomous scope (bounded to the sandbox `memo_eval`, explicitly excluding the production `decisions` collection) standing in for a live "yes" — which the PR body discloses openly rather than glossing over. It never touched production, so this isn't a safety breach, but it is a process substitution worth naming rather than nodding through.

### Deep-dive scrutiny items (per audit instructions)

1. **FR-2.8 / AC-2.7 hard guarantees — structurally verified, not just test-name-trusted.**
   - Dry-run writes nothing: `src/commands/migrate.ts` has exactly one write call (`qdrant.batchSetPayload`) in the entire file, and it is unconditionally gated behind `if (!dryRun && plan.ops.length > 0)`. There is no code path in `--dry-run` mode that reaches a write.
   - Idempotent by construction (not just observed): the Qdrant-side filter `is_empty: { key: 'schema_version' }` excludes already-migrated points from the very next `scrollAll` call, and `planMigration` independently re-checks `schema_version === '2'` and skips. Two independent layers guarantee re-running is a no-op — this is a structural guarantee, not an artifact of test fixture design.
   - No `delete*` call anywhere reachable from this command: confirmed by direct grep of `src/commands/migrate.ts` and `src/lib/migrate.ts` — zero occurrences of any delete-family call. `QdrantRepository.deleteById`/`deleteByFilter` exist in `src/lib/qdrant.ts` but are never referenced from the migrate command or library.

2. **Rule table exactness.** Rule 1 (`tags_any: ['intent','outcome']` → episodic, `session_id = story ?? 'legacy'`, `expires_at = timestamp_utc + 90d`) and rule 2 (catch-all → semantic, `valid_from = timestamp_utc`) match FR-2.8 verbatim, including the "any other entry defaults to semantic" safer-default rationale from PRD §7.2. The full "all" field set (`bank`, `schema_version="2"`, counters `0`, `stability` from `banks.kb.<kind>.initial_stability_days`, `stability_since`) is applied to every migrated point, confirmed both in code and in unit test assertions (`toMatchObject` on the complete field set).
   - **Minor/Undetermined note:** `stability` is only set `if (policy.initial_stability_days !== undefined)`. Since `KindPolicy.initial_stability_days` is an optional Zod field and the shipped `kb` defaults (3/90) always define it, this is unreachable with default config — but a custom config that explicitly unsets `initial_stability_days` would silently omit `stability` from the migrated payload, deviating from AC1's "every migrated point gets stability" wording. No test exercises this specific combination. Low real-world risk (would require a deliberately non-default config), but worth noting as a gap.

3. **§18.14 items 14/15 — landed exactly as resolved.**
   - Item 14 (a custom rule, including the catch-all, may set `kind: episodic`): `MigrationRuleSetSchema` places no restriction preventing `episodic` on any rule position; `§18.14 item 14` test explicitly exercises a catch-all rule with `kind: 'episodic'` and asserts it works.
   - Item 15 (bank preservation): `const bank = existingBank !== undefined && existingBank.trim().length > 0 ? existingBank : DEFAULT_BANK_ID` — preserves a pre-existing `bank`, defaults to `kb` otherwise. Directly tested (EC-3, plus an "out-of-domain probe" for a non-`kb` pre-existing bank).

4. **Live evidence internal consistency.**
   - Dry-run and real-run counts match exactly (`scanned:44, migrated:44, skipped:0, by_rule:{"1":4,"2":40}` in both).
   - `by_rule` breakdown (4 episodic / 40 semantic on 44 total) is independently verifiable: `tests/fixtures/relevance/entries.json` has exactly 44 entries, and grep for `intent`/`outcome` tags in that fixture returns exactly 4 matches — the reported split is not just plausible, it matches the actual fixture data exactly.
   - Second-run idempotency (`scanned:0, migrated:0, by_rule:{}`) is consistent with the structural double-guard described above.
   - Post-migration `eval:relevance` result (96.4% overall; concept 100%, identifier 100%, cross-repo 83.3%, recency 100%) is not a new, unverified number — it matches, per-category, the pre-existing recorded floor from Story S1-08 (`docs/requirements/prd-004-long-lived-agent-memory.md` changelog 1.11), which was itself the last live re-recording. This is a strong, independently-checkable evidence chain, not a self-reported assertion taken on faith.

5. **`schema_version` index addition — additive-only.** The diff to `src/lib/qdrant.ts` adds one entry (`{ field: 'schema_version', schema: 'keyword' }`) to the existing `PAYLOAD_INDEXES` array; no existing index entries are modified or removed. `ensureIndexes()` (pre-existing logic, untouched) only creates missing indexes, never drops any.

6. **Safety perimeter — deliberate-override requirement confirmed, with one process nuance flagged.**
   - `DEFAULT_COLLECTION_NAME = 'decisions'` (pre-existing, shared by every command, not introduced by this PR) means `memo migrate --to-v2` behaves exactly like every other command: it targets `decisions` only when no override is given, and this diff adds no migrate-specific bypass, shortcut, or alternate default. Reaching `memo_eval` (or any non-production collection) requires the operator to deliberately set `MEMO_COLLECTION` — there is no "just run it" default that silently lands on a sandbox or silently lands on production differently from any other command. This is the correct, existing safety posture, unchanged by this story.
   - The PR's own live-evidence runs explicitly set `MEMO_COLLECTION=memo_eval` for every dry-run/real-run/second-run/eval invocation; `decisions` is never referenced as a target anywhere in the diff, tests, or command execution.
   - **Process nuance (flagged per audit instructions, not softened):** the task list (`workstream/tasks-prd-004-phase-2-plan.md` step 9.15, and the story's own "Apply step: requires explicit user confirmation") called for a human-confirmation checkpoint before the real (non-dry-run) apply. What was actually recorded is the developer's own pre-approved autonomous scope — restricted to `memo_eval`, explicitly excluding `decisions` — standing in for that confirmation, with the PR body stating this directly: "not as a bypass of the confirmation gate, but as the form that gate takes in this delegated, non-interactive execution mode." No production collection was ever touched, and the disclosure is transparent rather than hidden. Still, this is a substitution of an autonomy-scope check for the human-in-the-loop confirmation the story text describes, and it should be named plainly rather than treated as equivalent.
