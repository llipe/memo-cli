## 1. Source Input Summary

Story S2-08 delivers three `memo bank` subcommands (`init`, `list`, `show`) plus a `banks` facet on `memo inspect`. It depends on S2-04 (`memo write` v2) for the actual write path and reuses `aggregateField` from the already-shipped `src/lib/facets.ts` for `list`.

Key normative constraints pulled from source artifacts:

- **PRD §2.4 B5:** `bank init` creates a bank _by writing its first `self` entry_ — there is no separate bank registry. `bank list` shows bank ids with per-kind counts. `bank show` prints the `self` entries and counts.
- **Spec §18.10 / decision A13:** `init` validates the id as `KebabOrUuid` and rejects the literal `kb` with `VALIDATION_FAILED` (`kb` is reserved as the fallback/no-bank corpus). `count({ bank: id }) > 0` short-circuits to "print existing summary, write nothing, exit 0". Otherwise it delegates to the S2-04 write handler with fixed flags (`kind: self`, `source: manual`, `entryType: structure`, default `rationale`/`tags` unless overridden). `--set-default` is the _only_ path that calls `writeConfig`; its absence means `writeConfig` must never be called (this is a build-vs-intent invariant, not just an assertion of the happy path).
- **`list`:** `aggregateField(scroll, 'bank')`, folding points with no `bank` field (v1 legacy points) into `kb`; three `count()` calls per discovered bank (one per kind: `self`, `episodic`, `semantic`).
- **`show`:** non-superseded `self` entries newest-first; counts per kind and per state (`active`/`archived`/`superseded`); `last_session_id` sourced the same way as the `recall` `LAST SESSION` section (§18.9); unknown bank id returns zero counts and a notice, exit 0 (not an error).
- **`inspect`:** adds a `banks` facet (counts only) to the existing `aggregateMultipleFields` output without changing `orgs`/`repos`/`domains` behavior.
- **Migration:** explicitly opted out (see §7 below) — this is a data-writing feature, not a schema migration, so no `migrate`-style apply/rollback test surface is designed.

At authoring time, `src/commands/bank.ts` does not exist in the codebase (confirmed via `find`/`ls`); `src/commands/inspect.ts` currently exposes `orgs`/`repos`/`domains` only, and `src/lib/facets.ts` ships `aggregateField(field, scroll, filter?)` (note: the _call-site parameter order_ in the spec's prose, `aggregateField(scroll, 'bank')`, is reversed relative to the actual exported signature `aggregateField(field, scroll, filter?)` — tests **MUST** call it as `aggregateField('bank', scroll)` and this plan flags the discrepancy as an implementation note, not a design defect, since `verifier` Audit Mode will confirm the eventual call-site is correct against the real signature).

## 6. Randomized Test Tactics (`activity-random-test-tactics`)

Targets the `KebabOrUuid` id validator with property-based / fuzz-style generation. All randomized runs **MUST** capture and log the seed for deterministic replay.

- **Seed policy:** Use a fixed seed per CI run captured from `process.env['TEST_SEED'] ?? Date.now()`, logged at the start of the test file (`console.log` gated behind a `DEBUG_SEED` env var, or attached to the Jest test name via `test.each`). On failure, the seed and the exact failing input **MUST** be printed in the assertion failure message so it can be re-run with `TEST_SEED=<n>` deterministically.
- **Generator strategy:** A small deterministic PRNG (e.g., mulberry32 seeded from the captured seed) feeding three generator lanes:

| Test ID | Generator lane                                                                                                                                                                                                                                     | Sample count                                                                                                | Expected validator outcome                                                                                                                                                                                                                                                                                             | AC  |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --- |
| RT-01   | Valid kebab strings: `/^[a-z][a-z0-9]*(-[a-z0-9]+)*$/`, lengths 1–63 chars, generated by concatenating random lowercase-alnum segments joined with single hyphens (never leading/trailing hyphen, never double hyphen)                             | 50 per run                                                                                                  | Every sample is **accepted** by the id validator (assuming it reuses or mirrors `KEBAB_CASE` from `src/types/entry.ts`) and, when passed to `init`, results in `VALIDATION_FAILED` only if it happens to equal exactly `kb`                                                                                            | AC1 |
| RT-02   | Valid UUID v4 strings via `randomUUID()` (Node's own generator, already used elsewhere in the codebase, e.g. `write.ts`)                                                                                                                           | 20 per run                                                                                                  | Every sample is **accepted** by the id validator                                                                                                                                                                                                                                                                       | AC1 |
| RT-03   | Invalid strings: random mutations of a valid kebab string (inject uppercase char, inject `_`, inject leading/trailing hyphen, inject double hyphen, inject whitespace, inject empty string, inject unicode/emoji, inject a string exactly 0 chars) | 50 per run, at least one from each mutation category deterministically included (not left purely to chance) | Every sample is **rejected** with `VALIDATION_FAILED`; zero writes attempted on the mocked repo for any rejected sample                                                                                                                                                                                                | AC1 |
| RT-04   | Adversarial near-misses of the reserved word: `kb`, `KB`, `Kb`, `kb ` (trailing space), ` kb`, `kb-` , `kb1`                                                                                                                                       | Exhaustive (7 fixed cases, not randomized)                                                                  | Only the exact literal `kb` triggers the reserved-word rejection path; the others either pass validation (e.g., `kb1`, `kb-` if it parses as valid kebab) or fail for the _kebab-case_ reason rather than the _reserved-word_ reason — test asserts on the distinguishing error message/code path, not just "rejected" | AC1 |

**Failure triage:** any RT-0x failure follows the mandatory sequence — capture seed + input, isolate by re-running with the captured seed, minimize the input, classify (spec gap → escalate to `product-engineer`; implementation defect → file for `developer`; flaky/non-reproducing → log as `inconclusive`, cap retries at 3).

## 7. Migration Opt-Out Rationale

This story is explicitly **not** designed with migration-apply/rollback test scenarios, per the task-list's own opt-out note (`workstream/tasks-prd-004-phase-2-plan.md` line 63: "Migration artifacts are not required for tasks 1.0–8.0 ... the opt-out rationale is recorded per task") and the story's own Migration Requirements section ("Migration artifact: not required — writes go through the S2-04 path; no existing data changes").

Rationale: `bank init` writes exactly one _new_ `self` point via the already-tested S2-04 write path (`handleWrite`). It does not touch `schema_version`, does not rewrite any existing payload, and does not require a `filterLacking('schema_version')`-style backfill scan the way `memo migrate --to-v2` (S2-09) does. Consequently:

- No `planMigration`-equivalent pure function exists for this story to unit-test.
- No `--dry-run` / real-run / second-run-scans-zero triad applies (that triad belongs to S2-09's `migrate.test.ts`).
- The only "migration-adjacent" concern this plan does carry forward is the **1.2.x forward-compatibility caveat** already documented in the story ("a bank created by 1.3.0 is one `self` point; 1.2.x `memo list` would show it as an ordinary entry since 1.2.x has no `kind` filter") — this is captured as a documentation/PR-body requirement, not a test case, per the story's own instruction to "Document in the PR."

Instead, this plan substitutes an explicit **write-path invariant test** in place of a migration test, per the parent task instruction: `writeConfig` is called if and only if `--set-default` is passed (see E2E-09/E2E-10 and CT-03 above), which is the one config-mutation surface this story touches and therefore the appropriate analogue to a migration-apply assertion.
