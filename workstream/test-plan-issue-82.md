## 3. Contract Validation Scenarios (`activity-contract-test-design`)

The filter _shape_ returned by `buildBaseFilter`, and the merged shape returned by `buildSearchFilters`/`buildListFilters`, is a contract consumed downstream by every read command (`search`, `list`, `tags list`, `read`, and later `timeline`/`recall`) and by `buildLexicalScrollFilter`. Contract tests assert the **exact object shape** (not just "truthy filter"), since any structural drift (e.g., nesting instead of concatenation, or a `should` becoming a `must`) silently breaks bank isolation for every consumer.

| Contract-ID | Contract under test                                         | Assertion                                                                                                                                                                                                                                                                                                                                                          |
| ----------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CT-1        | `buildBaseFilter({bank:'kb', kind:'all'})` shape            | Deep-equals `{ must: [{ should: [{key:'bank',match:{value:'kb'}},{is_empty:{key:'bank'}}] }, {should:...}? ], must_not: [{key:'kind',match:{value:'self'}}, {key:'archived',match:{value:true}}, {key:'superseded',match:{value:true}}] }` — exact structural snapshot, asserting `should` is nested _inside_ the `bank` clause only, never promoted to top level. |
| CT-2        | `buildBaseFilter({bank:'jarvis-memory', kind:'all'})` shape | `must` contains `{key:'bank',match:{value:'jarvis-memory'}}` (exact match, no `should`/`is_empty`).                                                                                                                                                                                                                                                                |
| CT-3        | Downstream builder signature parity                         | `buildSearchFilters(input, base)` and `buildListFilters(input, base)` retain their existing parameter list (adding `base` does not remove/rename any existing input field) — a type-level + snapshot test against the pre-story fixture inputs used in the current `search-filters.test.ts`/`list-filters.test.ts`.                                                |
| CT-4        | Merge is concatenation, not nesting                         | Given `base = {must:[A], must_not:[B], should:[C]}` and builder-produced `{must:[D], should:[E]}`, the merged result is `{must:[A,D], must_not:[B], should:[C,E]}` — asserted by array identity/order, not just set membership, and by asserting the result contains **no** key named `must` inside another `must` entry (guards against accidental nesting).      |
| CT-5        | `repo` clause conditionality contract                       | For `bank !== 'kb'` and no explicit `--repo`, the merged filter's `must` array contains **no** entry with `key: 'repo'`. For `bank === 'kb'` (repo required upstream) or an explicit `--repo` on any bank, the `repo` entry is present exactly once.                                                                                                               |
| CT-6        | `buildLexicalScrollFilter` base propagation                 | (Documented as a contract for S2-07/search.ts to honor; this story only needs `filters.ts`/`bank.ts`/`dedupe.ts` in isolation — recorded here as a **downstream consumer expectation**, not testable until `search.ts` lands. Traceability matrix marks this row `Deferred to S2-07`.)                                                                             |
| CT-7        | `policyFor` return-shape contract                           | For `bank='kb'`, return type/keys match `KindPolicy` (`initial_stability_days?`, `expires_in_days?`, `archive_threshold?`, `archive_noisy?`, `promoted_grace_days?`, `superseded_grace_days?`, `purge_after_days?`) with **no** `soft_cap` key. For any private bank + `kind='self'`, return type/keys match `SelfPolicy` (`soft_cap` only, integer, positive).    |
| CT-8        | `buildDedupeKeyV2` key-format contract                      | Semantic key literal shape `v2                                                                                                                                                                                                                                                                                                                                     | <bank> | <repo | na> | <commit | na> | <story | na> | na  | semantic | <entry_type> | <source>`; episodic key literal shape `v2 | <bank> | <repo | na> | <commit | na> | <story | na> | <session> | <seq> | episodic | <entry_type> | <source>`; `self` key is a 64-hex-char SHA-256 digest (format only, value unconstrained). |

## 4. Edge-Case Catalog (`activity-edge-case-refinement`)

Categorized per the standard taxonomy (input domain, state transition, timing/boundary, idempotency, failure modes, auth/permissions N/A here, data boundaries, resource exhaustion N/A here, API versioning N/A here). This story is dominated by **input-domain** and **timing/boundary** cases around resolution order and `as-of`.

### 4.1 Bank resolution order (AC1) — input domain / precedence

| Edge-ID | Case                                                                                             | Expected                                                                                                                                                             |
| ------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EC-1    | `flag`, `env`, `config.bank.default` all set to different valid banks                            | `flag` wins                                                                                                                                                          |
| EC-2    | `flag` unset, `env` and `config.bank.default` set                                                | `env.MEMO_BANK` wins                                                                                                                                                 |
| EC-3    | `flag` and `env` unset, `config.bank.default` set                                                | `config.bank.default` wins                                                                                                                                           |
| EC-4    | Nothing set anywhere                                                                             | `'kb'`                                                                                                                                                               |
| EC-5    | `MEMO_BANK=""` (empty string)                                                                    | Treated as **unset** — falls through to `config.bank.default` or `'kb'`, not treated as an invalid non-kebab value and not treated as a valid bank named `""`        |
| EC-6    | `MEMO_BANK` is whitespace-only (`"   "`)                                                         | Same as EC-5 — treated as unset (defensive extension of the story's explicit edge case)                                                                              |
| EC-7    | `MEMO_BANK="KB"` (uppercase, not kebab-case)                                                     | `VALIDATION_FAILED`, source named `MEMO_BANK`                                                                                                                        |
| EC-8    | `--bank "Not_Valid!"` (flag invalid)                                                             | `VALIDATION_FAILED`, source named `--bank` — and env/config are **not** consulted as a fallback (invalid flag fails fast, does not degrade to next precedence level) |
| EC-9    | `config.bank.default` invalid (e.g., contains uppercase) while flag/env unset                    | `VALIDATION_FAILED`, source named `config.bank.default`                                                                                                              |
| EC-10   | `--bank` valid kebab but `MEMO_BANK` invalid                                                     | `flag` wins; the invalid env value is never evaluated/thrown (precedence short-circuits before validating lower-priority sources)                                    |
| EC-11   | Valid UUID as bank id (`KebabOrUuid` per config schema) at each of `flag`/`env`/`config.default` | Accepted, not rejected as "not kebab"                                                                                                                                |
| EC-12   | `flag = 'kb'` explicitly passed even though env/config differ                                    | Resolves to `'kb'` (flag always wins regardless of value)                                                                                                            |

### 4.4 `buildBaseFilter` (AC4) — timing/boundary, data boundaries, state transition

| Edge-ID | Case                                                                        | Expected                                                                                                                                                                                                              |
| ------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EC-23   | `kind='self'` alone (no `includeSuperseded`)                                | `must kind='self'` + default exclusions still applied (archived/superseded excluded)                                                                                                                                  |
| EC-24   | `kind='self'` with `includeSuperseded=true`                                 | Superseded `self` entries are returned — `must_not superseded=true` is lifted while `must_not archived=true` remains (independence of the two flags) — this exercises the story's explicit edge case                  |
| EC-25   | `includeArchived=true`, `includeSuperseded=false`                           | Only the `archived` exclusion is lifted; `superseded` exclusion remains                                                                                                                                               |
| EC-26   | `includeArchived=false`, `includeSuperseded=true`                           | Only the `superseded` exclusion is lifted; `archived` exclusion remains                                                                                                                                               |
| EC-27   | `includeArchived=true` and `includeSuperseded=true`                         | Both exclusions lifted; `must_not` has no `archived`/`superseded` entries                                                                                                                                             |
| EC-28   | `session` provided                                                          | `must` gains `{key:'session_id', match:{value:<s>}}` in addition to bank/kind/exclusion clauses (additive, not replacing)                                                                                             |
| EC-29   | `asOf` equal to a candidate's `valid_from`                                  | **Inclusive** — `valid_from <= asOf` (`lte`) — candidate is included                                                                                                                                                  |
| EC-30   | `asOf` equal to a candidate's `valid_to`                                    | **Exclusive** — `valid_to > asOf` (`gt`) — candidate is excluded                                                                                                                                                      |
| EC-31   | `asOf` provided, candidate has no `valid_to` (still current)                | Included via the `is_empty: {key:'valid_to'}` branch of the `should`                                                                                                                                                  |
| EC-32   | `asOf` provided without explicit `includeSuperseded`                        | `asOf` **implies** `includeSuperseded=true` — the `must_not superseded=true` clause is absent even though the caller didn't pass the flag                                                                             |
| EC-33   | `asOf` provided **and** `includeSuperseded=false` explicitly passed         | `asOf`'s implication wins — superseded exclusion still lifted (documents precedence: `asOf` cannot be overridden back to excluding superseded)                                                                        |
| EC-34   | No optional inputs at all (`bank`, `kind='all'` only)                       | Filter contains only bank clause + `must_not kind='self'` + default archived/superseded exclusions — no `session_id`, no `valid_from`/`valid_to`, no empty arrays left dangling                                       |
| EC-35   | `bank='kb'`, v1 point with no `bank` field, `kind` absent (v1 legacy point) | Passes the `is_empty` bank clause and is treated as semantic by the reader per Spec §18.7 (documented boundary; asserted at the filter-shape level only, since "reader" behavior itself is a different story's scope) |

### 4.5 Builder merge semantics (AC5) — data boundaries / idempotency

| Edge-ID | Case                                                                                         | Expected                                                                                                                                                                                                                                |
| ------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EC-36   | `base` has empty `must`/`must_not`/`should` arrays (or omits the keys entirely)              | Merges cleanly — no `undefined`/`null` entries appended, no empty array left in the final shape if a key would otherwise be empty (per the current builders' `...(x.length > 0 ? {must:x} : {})` convention) — explicit story edge case |
| EC-37   | `base` present, builder produces no clauses of its own (e.g., `list` called with no filters) | Merged result equals `base` verbatim (identity-like merge, not a mutation of `base`'s original object)                                                                                                                                  |
| EC-38   | `bank='kb'`, no explicit `--repo` passed but `repo` is required upstream by `kb` scoping     | `repo` clause is present (per current default behavior — `kb` always resolves repo)                                                                                                                                                     |
| EC-39   | `bank='jarvis-memory'` (private), no explicit `--repo`                                       | `repo` clause is **absent** from the merged filter                                                                                                                                                                                      |
| EC-40   | `bank='jarvis-memory'` (private), explicit `--repo` passed                                   | `repo` clause **is** present despite the bank being private                                                                                                                                                                             |
| EC-41   | Calling `buildSearchFilters`/`buildListFilters` twice with the same `base` object reference  | `base` object is not mutated between calls (no shared-array aliasing bug — mutating the returned filter must not affect a second call's output)                                                                                         |

### 4.6 Dedupe v2 (AC6/AC7) — idempotency / uniqueness / boundary

| Edge-ID | Case                                                                                               | Expected                                                                                                                                                        |
| ------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EC-42   | Semantic key, all optional fields (`repo`, `commit`, `story`) present                              | Key embeds actual values, no `'na'` placeholders                                                                                                                |
| EC-43   | Semantic key, `commit`/`story` undefined                                                           | `'na'` substituted per §18.5 literal template                                                                                                                   |
| EC-44   | Semantic key never includes `session`/`seq` segments regardless of whether those params are passed | Passing a stray `session_id`/`seq` to the semantic branch has no effect on the output key (defensive: function should ignore fields not applicable to the kind) |
| EC-45   | Episodic key includes both `session` and `seq`, `seq=0`                                            | `0` is serialized as the literal `"0"`, not treated as falsy/omitted                                                                                            |
| EC-46   | Episodic key, `repo`/`commit`/`story` undefined                                                    | `'na'` substituted, `session`/`seq` still literal                                                                                                               |
| EC-47   | Same inputs, same `seq`, called twice                                                              | Identical key both times (deterministic, no hidden randomness in non-`self` branches)                                                                           |
| EC-48   | `seq=0` vs `seq=1`, all else identical                                                             | Different keys (AC7)                                                                                                                                            |
| EC-49   | `self` kind, same `id`/inputs, called twice                                                        | Two **different** keys (never matches — random per call, per AC6)                                                                                               |
| EC-50   | `self` key format                                                                                  | 64-character lowercase hex string (SHA-256 digest length), passes `/^[0-9a-f]{64}$/`                                                                            |

## 5. Randomized Testing Tactics (`activity-random-test-tactics`)

**Property under test:** `buildDedupeKeyV2({kind:'self', ...})` never produces a collision across repeated calls with otherwise-identical inputs (AC6).

| Field                  | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tactic                 | Property-based: call `buildDedupeKeyV2` 1,000 times with identical fixed input params (`bank`, `entry_type`, `source` held constant; `kind:'self'`) and assert `new Set(keys).size === 1000` (zero collisions).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Seed policy            | Use Jest's default PRNG only if the implementation is expected to use `randomUUID()` internally (non-seeded, OS-CSPRNG-backed) — this is **not** a seeded-PRNG property test, since the whole point is cryptographic/OS-level randomness, not a reproducible sequence. If the implementation instead accepts an injectable RNG for testability, capture and log the seed for replay per Non-Negotiable Operating Rule 6.                                                                                                                                                                                                                                                                                                                                  |
| Reproducibility        | Because `self` keys are intentionally non-deterministic, a failing run (a collision) is inherently non-reproducible by re-running with the same seed unless the RNG is injectable. Failure triage must fall back to **statistical** reproduction: re-run the 1,000-call batch N additional times (recommend N=10) and require zero collisions in every batch before ruling out a defect.                                                                                                                                                                                                                                                                                                                                                                  |
| Minimization           | On collision, log both colliding indices and the exact `randomUUID()`/entropy source values (if introspectable) so `developer` can inspect whether the underlying UUID source was mocked/stubbed accidentally in the failing environment (common root cause: an accidentally-global `Math.random` mock in test setup).                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Failure classification | A `self` collision found in this property test is classified **implementation defect** (contradicts AC6 directly), not spec gap, since AC6 is explicit about "never collide".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Secondary property     | `buildDedupeKeyV2` for semantic/episodic (deterministic branches) — run 100 randomized fixture generations (`fast-check`-style or manual randomized fixture builder) varying `repo`/`commit`/`story`/`entry_type`/`source`/`session`/`seq` and assert: (a) same fixture called twice yields identical key (determinism, extends EC-47), (b) any single-field change yields a different key (no accidental field-collapsing in the template), except where the spec intentionally normalizes (e.g., `undefined` vs `'na'` string — must be verified as an **intentional** collision, documented, not a bug: `commit=undefined` and `commit='na'` literally colliding is expected per the template and MUST be asserted as such, not treated as a failure). |
