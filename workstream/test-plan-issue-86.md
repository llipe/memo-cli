## 6. Randomized Test Tactics (`activity-random-test-tactics`)

Property-based / randomized coverage of the trimming-order algorithm, since exhaustive enumeration of section-size × budget combinations is impractical by hand.

- **Target under test:** `assembleRecall(inputs, budget)` (pure function, lib-level — ideal for property-based testing since it has no I/O).
- **Tooling:** `fast-check` (or equivalent JS property-testing library already in the repo's toolchain; if absent, hand-rolled seeded PRNG loop is an acceptable fallback — confirm with `developer` during implementation which is available).
- **Seed policy:** Every randomized run **MUST** capture and log its seed (e.g., via `fc.configureGlobal({ seed, ... })` or an explicit `mulberry32(seed)` generator) so a CI failure is reproducible with `--seed <n>`. Seed **MUST** be printed to test output on failure and recorded in the PR body per Testing Requirements.
- **Generators:**
  - Random counts per section: `self ∈ [0, 120]`, `policies ∈ [0, 20]`, `shared ∈ [0, 30]`, `mine ∈ [0, 20]`, `last_session ∈ [0, 40]`, `conflicts ∈ [0, 20]`.
  - Random rendered-line lengths per entry (`chars ∈ [10, 2000]`) to drive varied `ceil(chars/4)` token costs.
  - Random `max_tokens ∈ [0, 100000]`, including boundary values `0` and values exactly equal to a computed section-boundary sum.
  - Random duplicate-id injection: with probability `p ∈ [0, 0.3]`, clone an id from an earlier-generated section into a later section's candidate pool, to fuzz the dedup path (EC-04/EC-05) alongside trimming.
- **Invariants asserted on every generated run** (properties, not fixed expected values):
  1. **SELF invariant:** `self` output ids are always a subset of `self` input ids and are never fewer than the input's non-superseded count — SELF is never trimmed regardless of `max_tokens`.
  2. **Trim-order invariant:** if any of `conflicts, last_session, mine, shared, policies` was trimmed (output length < deduped-input length), every section strictly _before_ it in the order `policies → shared → mine → last_session → conflicts` (i.e., every section trimmed _later_ in AC3's trim sequence, reading right-to-left) is either untouched or was already fully emptied first — i.e., trimming never skips ahead out of order.
  3. **Dedup invariant:** the multiset of all output ids across all sections has no duplicates (property: `new Set(allIds).size === allIds.length`).
  4. **Budget-honesty invariant:** `budget.used_tokens` always equals the recomputed sum of `ceil(chars/4)` over exactly the ids present in the output — never a stale/precomputed value from before trimming.
  5. **Truncated-list invariant:** a section name appears in `truncated` if and only if its output count is strictly less than its deduped-and-capped input count (no false positives/negatives).
  6. **Monotonicity invariant:** for a fixed input, increasing `max_tokens` never decreases the token count of any single section's output (trimming relaxes monotonically as budget grows).
- **Minimization on failure:** on a counter-example, shrink to the smallest section-size/`max_tokens` combination that still reproduces the invariant violation (property-testing libraries do this automatically; if hand-rolled, apply the Failure Triage Workflow's Minimize step manually).
- **Retry budget:** per the Failure Triage Workflow, a non-reproducing (flaky) property failure is retried at most 3 times with the same captured seed before being classified `inconclusive` and logged with environment details.
